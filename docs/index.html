The .htaccess rulesOpenLiteSpeed ignores.

OpenLiteSpeed parses RewriteRule itself. Header, Redirect, Require, FilesMatch, Expires and the rest are dropped. hatch loads into the server and applies them per request, the way Apache does. Edit the file, and the next request obeys it. No restart.

curl -fsSL https://raw.githubusercontent.com/prabowosd/hatch/main/install.sh | sudo bash

Checks glibc and architecture, verifies the release, restores itself if the server does not come back. Directive reference ↓

.htaccesswritten by hand
Header always set X-Frame-Options "SAMEORIGIN"
Header set Cache-Control "public, max-age=31536000"
ExpiresByType text/css "access plus 1 year"
Require ip 203.0.113.0/24
RedirectMatch 301 ^/old/(.*)$ /new/$1
responsesame request
HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000
Expires: Wed, 03 Nov 2027 00:00:00 GMT
X-Frame-Options: SAMEORIGIN
Content-Type: text/css; charset=utf-8
Same rules, from 192.0.2.9: 403 Forbidden. From inside the range, or for a rewritten path, the response follows Apache's order.

01 / Install

Install

The installer checks the architecture and glibc (2.34 or newer: RHEL, Alma and Rocky 9 and 10, Ubuntu 22.04+), verifies the release checksum, backs up httpd_config.conf and any previous module, adds the module hatch block, and does a graceful restart. If OpenLiteSpeed does not come back with hatch loaded, it restores the previous module and config on its own.

It edits an OpenLiteSpeed that is already installed on the host. The block it adds:

httpd_config.conf
module hatch {
  ls_enabled              1
}

Options

--file ./libhatch.so
Install a local build instead of a release.
--version v0.1.0
Pin a release.
--status
Report what is installed, and whether the Webuzo guard and watcher are present.
--uninstall
Remove the module, the guard and the watcher.
--no-guard
Skip the Webuzo config guard.
--no-watch
Skip the .htaccess watcher.

02 / Directives

Directive reference

Everything here is read from .htaccess on each request, so an edit applies to the next one. Unsupported lines are logged once per file change and skipped; they never break the site.

RequestHeader cannot be implemented. LSIAPI can read a request header, but no call changes one. The line is logged and skipped. Basic Auth (AuthType, AuthUserFile, Require valid-user) is next, in v0.2.

Response headers and environment

Header set|append|merge|add|edit|unset
always and onsuccess accepted. set replaces values the server added itself; edit substitutes a pattern in the value already set, and edit* replaces every match. env=name and env=!name conditions apply; expr= is reported and ignored.
SetEnv, UnsetEnv
Sets and clears request environment variables, so the backend and the rewrite engine see them.
SetEnvIf, SetEnvIfNoCase, BrowserMatch, BrowserMatchNoCase
Matches a request header, Request_URI, Request_Method, Remote_Addr, Remote_Host or Host. !var and var=value are accepted.
AddDefaultCharset
Adds a charset to the response Content-Type when the response has none; Off disables it.

Access control

Order, Allow from, Deny from
Apache 2.2 semantics, IPv4, IPv6, CIDR and partial addresses (10.1).
Require all granted|denied, Require ip, Require not ip
Apache 2.4 semantics.
Satisfy Any|All
Combines host rules (Order, Allow, Deny) with Require rules using OR (Any) or AND (All).
<Limit>, <LimitExcept>
Access rules apply only to the listed HTTP methods, or to every method except them.
SSLRequireSSL
Answers 403 when the request did not arrive over TLS.
<Files>, <Files ~>, <FilesMatch>
Applied to the requested file name.
<IfModule>
Contents apply; <IfModule !...> fallbacks are skipped.

Redirects and documents

Redirect, RedirectPermanent, RedirectTemp
Prefix match that keeps the rest of the path, like mod_alias. Status words permanent, temp, seeother, gone.
RedirectMatch
Regex with $1..$9. Targets must be a path or an http(s) URL.
ErrorDocument
A path target, for a 404 and for a denied request, and for any other 4xx or 5xx the backend returns (401, 500, 503). The page is served through an internal redirect and keeps the original status. URL and text targets need a body hatch cannot write, so they are logged and skipped.
DirectoryIndex
Serves the first listed file that exists, e.g. DirectoryIndex index.php index.html; disabled turns it off. Only plain file names are accepted.
Options -Indexes
A directory with no index file answers 403 instead of listing its contents. +Indexes restores the server default. Symlink and content-negotiation options (FollowSymLinks, SymLinksIfOwnerMatch, MultiViews) are accepted and left to the server.

Caching and expiry

ExpiresActive, ExpiresDefault, ExpiresByType
access plus N unit and A<seconds> forms, type/* wildcards. Like mod_expires, a PHP or proxied response that sets its own Cache-Control or Expires keeps it; Header set Cache-Control still wins over expiry.
CacheEnable public|private, CacheDisable, CacheMaxExpire
Emits X-LiteSpeed-Cache-Control so the LiteSpeed cache engine caches matching URLs (public,max-age=N, private,max-age=N, or no-cache). Paths match at or below the prefix, and the last matching directory rule wins. A backend header already set wins, a backend that set its own Cache-Control or Expires keeps it, and Header set X-LiteSpeed-Cache-Control wins over the directives.

PHP

php_value, php_admin_value, php_flag, php_admin_flag
Needs CyberPanel's OpenLiteSpeed core, whose API carries the php config calls. On other cores the line is logged once and skipped.

Left to OpenLiteSpeed

RewriteEngine, RewriteRule, RewriteCond, RewriteBase
Parsed by OpenLiteSpeed at config load and cached, so a rewrite edit waits for a reload. hatch does not touch them.

03 / Mechanics

How it works

Two hooks, both per request. URI_MAP runs before the server picks a handler, and owns redirects and access control. SEND_RESP_HEADER runs once the response headers exist, and owns headers, expiry, LiteSpeed cache control, and error pages for a status only the backend knows.

  1. requestGET /shop/cart/
  2. URI_MAPredirect · access · errors
  3. handlerstatic, PHP, proxy
  4. SEND_RESP_HEADERheaders · expiry · cache
  5. response200 · 301 · 403 · 503

Accent cells are hatch. URI_MAP: Redirect, Require, ErrorDocument 403/404, DirectoryIndex. SEND_RESP_HEADER: Header, Expires, Cache-Control, backend error pages.

For each request it walks from the document root down to the file's folder and merges every .htaccess on the way, the way Apache's per-directory context does.

/public/.htaccess — headers and SetEnv accumulate
/public/shop/.htaccess — access rules replace the parent's
/public/shop/cart/.htaccess — the deepest matching redirect wins
one merged decision per request

Safety

  • Parsed files are cached per worker and re-read only when their mtime or size changes. Files over 256 KB are ignored.
  • Regexes use the regex crate, which runs in linear time, so a hostile pattern cannot stall a worker.
  • Header names, values and redirect targets are validated; anything that could inject a header or a javascript: redirect is dropped.
  • Every hook runs inside catch_unwind and fails open: a bug in hatch skips the .htaccess rules for that request instead of taking the server down.
  • The server's function table is read once per worker. CyberPanel's core has a longer lsi_api_t, so hatch picks the layout from the core's ABI marker first and falls back to scanning the server binary.

04 / Hosting panels

Hosting panels

Two panels run OpenLiteSpeed today and are supported here: CyberPanel and Webuzo. They differ in what they put in the module table and in who owns the config file. Panels that serve Apache, nginx or LiteSpeed Enterprise cannot load an OpenLiteSpeed module; they are listed at the end of this section.

CyberPanel v0.1.2+

CyberPanel replaces OpenLiteSpeed with its own core (2.5.x), whose lsi_api_t carries three extra members. hatch detects that layout at load time by the cyberpanel_lsi_api_abi_v1 symbol the core exports, and reads the table with that layout. On a core with an unknown marker it logs one line and stays idle instead of guessing.

v0.1.1 and older crash the worker on the first request there, so upgrade before installing. The bundled cyberpanel_ols module needs a paid license and stays inert without one; hatch runs next to it.

php_value and php_flag work only here, because the php config calls exist only in this core.

Webuzo

Webuzo 4.x runs a stock OpenLiteSpeed core, so the module needs no special build. Its vhosts use configFile and autoLoadHtaccess 1, with document roots under /home/<user>/<domain>/public. hatch asks the server for the document root, so the .htaccess beside the site is found either way.

Webuzo rewrites httpd_config.conf and every vhost under conf/webuzo_vh/ from its own state, so a hand-added module hatch block can disappear. When the installer sees Webuzo, it adds /usr/local/bin/hatch-guard with a one-minute cron: the guard puts the block back and restarts OpenLiteSpeed only when it has been removed.

It also adds hatch-reload, a systemd service that watches the document roots with inotifywait, debounces two seconds, and reloads at most once every ten seconds, so a RewriteRule edit applies within seconds instead of waiting for the panel's own two-minute cron. It needs inotify-tools.

php_value and php_flag are logged and skipped on Webuzo's stock core. OpenLiteSpeed has no module API for per-request PHP configuration; phpIniOverride in a vhost or context block is the static alternative, and Webuzo keeps per-domain files for it under /var/webuzo-data/openlitespeed/custom/.

Panels hatch does not load on

hatch is an OpenLiteSpeed module, so it only runs where OpenLiteSpeed is the server. On a panel that serves Apache, nginx or LiteSpeed Enterprise, .htaccess is already read by the server itself, and there is no OpenLiteSpeed function table to load into.

cPanel
Apache, or LiteSpeed Enterprise as a drop-in replacement. Both process .htaccess natively; the OpenLiteSpeed module API is not present.
DirectAdmin
Apache, nginx, or LiteSpeed Enterprise. Same reason: no OpenLiteSpeed core, and .htaccess is already native.
Plesk
nginx in front of Apache or PHP-FPM. nginx does not read .htaccess, and hatch does not change that.
LiteSpeed Enterprise
LiteSpeed's own Apache-compatible core reads .htaccess itself. hatch targets OpenLiteSpeed's lsi_api_t, so it is not needed there.

05 / Docker

Docker

For a container, mount the release .so and a config that enables it instead of running the installer.

compose.yaml
services:
  openlitespeed:
    image: litespeedtech/openlitespeed:latest
    volumes:
      - ./hatch-x86_64-linux-gnu.so:/usr/local/lsws/modules/hatch.so:ro
      - ./httpd_config.conf:/usr/local/lsws/conf/httpd_config.conf:ro

Use the x86_64 or aarch64 asset that matches the container. The image must use glibc (the official OpenLiteSpeed images do); a musl or Alpine image cannot load the module.

06 / Build

Build

The module links against OpenLiteSpeed's LSIAPI (ols-api/, GPLv3, from OpenLiteSpeed 1.8.3). Builds run in a container so the result matches the target glibc.

shell
podman build -t hatch-build -f build/Containerfile build
podman run --rm -v "$PWD":/src:Z hatch-build cargo build --release
# target/release/libhatch.so

07 / Test

Test

shell
podman run --rm -v "$PWD":/src:Z hatch-build cargo test  # unit tests
tests/integration.sh target/release/libhatch.so          # real OpenLiteSpeed in a container
HATCH_CYBERPANEL=1 tests/integration.sh libhatch.so      # CyberPanel's core (x86_64)
HATCH_LOCAL=1 tests/integration.sh libhatch.so           # the server installed on this host

CI runs all of them on x86_64 and aarch64: OpenLiteSpeed 1.8 (official image), 1.9 on AlmaLinux 10 (LiteSpeed RPM), and CyberPanel's core built from build/CyberPanelfile.

08 / Debugging

Troubleshooting

When the module loads but a rule does not apply, create /usr/local/lsws/conf/hatch.debug and restart. hatch then logs, per request, what the server handed it: the URI, the document root, the resolved file path and how many .htaccess files apply.

shell
sudo touch /usr/local/lsws/conf/hatch.debug
sudo /usr/local/lsws/bin/lswsctrl restart
tail -f /usr/local/lsws/logs/error.log | grep '\[hatch\]'

The check runs once per worker thread, so a restart is required after creating or removing the file. Entries are written at WARN level to the vhost error log, so an errorlog block with logLevel ERROR will suppress them. Remove the file and restart when done, since an active trace writes several lines per request.

09 / FAQ

Questions

Does hatch work on CyberPanel?

Yes, from v0.1.2. CyberPanel replaces OpenLiteSpeed with its own core (2.5.x) whose lsi_api_t carries three extra members; hatch reads the layout from the core's ABI marker at load time. php_value and php_flag work on CyberPanel only, because the php config calls exist only in that core.

Does hatch work on Webuzo?

Yes. Webuzo ships a stock OpenLiteSpeed core, so the release build loads unchanged. The installer adds a config guard, because Webuzo rewrites httpd_config.conf from its own state, and a watcher that reloads OpenLiteSpeed when a .htaccess changes. The watcher needs inotify-tools.

Does hatch work on cPanel, DirectAdmin or Plesk?

No. Those panels serve Apache, nginx or LiteSpeed Enterprise. Apache and LiteSpeed Enterprise already process .htaccess themselves, nginx does not read it at all, and none of them expose the OpenLiteSpeed module API that hatch loads into.

Do I need to restart OpenLiteSpeed after editing .htaccess?

No, not for the directives hatch applies. They are read from .htaccess on each request, so an edit applies to the next one. RewriteRule is the exception: OpenLiteSpeed parses it at config load and caches it, so a rewrite edit waits for a reload. On Webuzo the installer's watcher does that within seconds.

Does hatch replace mod_rewrite?

No. RewriteEngine, RewriteRule, RewriteCond and RewriteBase are left to OpenLiteSpeed, which already handles them. hatch fills in the families the server ignores: headers, redirects, access rules, error documents, expiry and LiteSpeed cache control.

Does the module slow down requests?

Two hooks run per request. Parsed files are cached per worker and re-read only when their mtime or size changes, so a warm request costs one stat per .htaccess on the path. Regexes use the regex crate, which runs in linear time, and every hook fails open inside catch_unwind.

How do I check that hatch is loaded?

The module logs one line at load. install.sh --status reports what is installed, and creating /usr/local/lsws/conf/hatch.debug turns on a per-request trace in the vhost error log.
